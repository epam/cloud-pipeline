# An archive extraction fails once its uncompressed content exceeds `maxSizeBytes` configured in `system.async.tasks.config`

Test verifies that `maxSizeBytes` in the `tasks.storageUnpackArchive` section of the **`system.async.tasks.config`** preference is enforced in two
different ways, depending on whether the archive's own format reveals its uncompressed total:
- a ZIP declares it in its central directory, so an oversized ZIP finishes `FAILED` before a single
 file is written, with a message saying what it **declares**
- a BZIP2 stream declares nothing about its content, so the same limit is only caught while writing:
 the task finishes `FAILED` once the bytes already written pass the limit, with a message saying
 what the archive **holds**

**Prerequisites**:
- Admin user
- A user with **READ** and **WRITE** permissions on an S3 object storage (or an NFS storage whose
 share is mounted as NFS)

**Preparations**:
1. Login as the admin user from the Prerequisites
2. Open the **Settings** page. Click the **PREFERENCES** tab, then the **Data storage** tab
3. Find the **`system.async.tasks.config`** preference and save its current value
4. Set its `tasks.storageUnpackArchive.maxSizeBytes` field to `10`, keeping every other field as
 is. Click **Save**
5. Login as the user from the Prerequisites and open the storage from the Prerequisites
6. On the local machine, have ready:
 - a ZIP archive (e.g. `archive1.zip`) holding one ordinary file of more than 10 bytes
 - a bare BZIP2 file (e.g. `data.csv.bz2`, not a `.tar.bz2`) whose decompressed content is more
 than 10 bytes
7. Upload both files into the storage via **Upload** → **Upload**, so nothing is queued yet

| Steps | Actions | Expected results |
| :---: | --- |---|
| 1 | Select `archive1.zip` alone, click the selection button (**"1 item selected"**) and click **Extract archive** | A message confirms the extraction has been queued |
| 2 | Open the **Storage tasks** window (the grid-icon button at the top right of the storage view, then **Show storage tasks**) and wait until that task's status stops changing | The task's status becomes `FAILED` |
| 3 | Hover the **Status** cell of that row | A tooltip reading `The archive declares <size> of content, and 10 B is the most one archive may be extracted into. Split it, or ask an administrator to raise the limit. Nothing was written to the destination.` appears, `<size>` being the file's uncompressed size |
| 4 | Look at the storage listing | No folder was created beside `archive1.zip` - the ZIP was refused before anything was extracted |
| 5 | Close the window. Select `data.csv.bz2` alone, click the selection button and click **Extract archive** | A message confirms the extraction has been queued |
| 6 | Open the **Storage tasks** window again and wait until that task's status stops changing | The task's status becomes `FAILED` |
| 7 | Hover the **Status** cell of that row | A tooltip reading `The archive holds more than 10 B of content, which is the maximum one archive may be extracted into. Split it, or ask an administrator to raise the limit. Nothing was written to the destination.` appears - worded differently from step 3, since nothing was declared up front |
| 8 | Look at the **Actions** column of both failed rows | Neither offers a **Download** button |

**After**:
- Delete `archive1.zip` and `data.csv.bz2` from the storage, and any folder or partial file either
 left behind
- Restore the `system.async.tasks.config` preference to the value saved at step 3 of Preparations
