# [Negative] Download archive pop-up stays open when the per-user download cap is hit on confirm

Test verifies that:
- when the per-user archive-download cap (the `maxUserTasks` field of the `storage.download.archive.config` preference) is reached after the **Download archive** pop-up was opened but before **OK** is clicked, confirming raises a notification explaining the cap instead of queuing the archive
- the pop-up stays open, the **Archive name** field, **Cancel** and **OK** re-enable, and **OK** can be pressed again once the cap clears

**Prerequisites**:
- Admin user
- A user with **READ** and **WRITE** permissions on an S3 object storage (or an NFS storage whose share is mounted as NFS), holding at least two files
- Two browser tabs signed in as that user (`Tab A` and `Tab B`)

**Preparations**:
1. Login as the admin user from the Prerequisites
2. Open the **Settings** page. Click the **PREFERENCES** tab, then the **Data storage** tab
3. Find the **`storage.download.archive.config`** preference and save its current value
4. Change its `maxUserTasks` field to `1`, keeping every other field as is. Click **Save**
5. In `Tab A`, login as the user from the Prerequisites and open the storage from the Prerequisites

| Steps | Actions | Expected results |
| :---: | --- | --- |
| 1 | In `Tab A`, select one of the storage's files via its checkbox | |
| 2 | Click the selection button (**"1 item selected"**) and choose **Download archive** | The **Download archive** pop-up opens in `Tab A` with no active downloads yet, so the cap check passes. **OK** is enabled. Leave this pop-up open |
| 3 | Open `Tab B`, open the same storage, select a different file via its checkbox | |
| 4 | In `Tab B`, click the selection button and choose **Download archive**, then click **OK** without changing the offered name | The pop-up in `Tab B` queues the task and closes. The notification `Archive download has been queued. Follow its progress under "Show downloads".` appears. One archive-download task is now in progress for the user, equal to the `maxUserTasks` value set in Preparations |
| 5 | Switch to `Tab A`. Without changing the **Archive name** field, click **OK** | <li> **OK** briefly shows a loading spinner <li> a notification appears explaining the cap, e.g. `You already have 1 archive downloads in progress, and the limit is 1. Wait for one to finish before starting another.` <li> the pop-up in `Tab A` stays open <li> the **Archive name** field, **Cancel** and **OK** re-enable, and **OK** no longer shows the spinner |
| 6 | Open the **Downloads** window (the grid-icon button at the top right of the storage view, then **Show downloads**) and cancel the task queued at step 4 | The task's status changes away from active (e.g. to `CANCELLED`), freeing the cap slot |
| 7 | Switch back to `Tab A`. With the pop-up still open and the name unchanged, click **OK** again | The cap check now passes: the archive-download task is queued, the notification `Archive download has been queued. Follow its progress under "Show downloads".` appears, and the pop-up in `Tab A` closes |

**After**:
- Cancel or let finish any remaining queued task(s) from the **Downloads** window
- Restore the `storage.download.archive.config` preference to the value saved at step 3 of Preparations
