# An archive extraction fails once its entries exceed `maxFilesCount` configured in `system.async.tasks.config`

Test verifies that `maxFilesCount` in the `tasks.storageUnpackArchive` section is enforced in two
different ways, depending on whether the archive's own format reveals its entry count:
- a ZIP declares it in its central directory, so an archive with too many entries finishes `FAILED`
 before a single file is written, with a message saying what it **declares**
- a TAR.GZ does not declare its entry count, so the same limit is only caught while extracting: the
 task finishes `FAILED` once the entries already seen pass the limit, with a message saying what
 the archive **holds**

**Prerequisites**:
- Admin user
- A user with **READ** and **WRITE** permissions on an S3 object storage (or an NFS storage whose
 share is mounted as NFS)

**Preparations**:
1. Login as the admin user from the Prerequisites
2. Open the **Settings** page. Click the **PREFERENCES** tab, then the **Data storage** tab
3. Find the **`system.async.tasks.config`** preference and save its current value
4. Set its `tasks.storageUnpackArchive.maxFilesCount` field to `2`, keeping every other field as
 is. Click **Save**
5. Login as the user from the Prerequisites and open the storage from the Prerequisites
6. On the local machine, have ready:
 - a ZIP archive (e.g. `archive1.zip`) holding 3 ordinary files
 - a TAR.GZ archive (e.g. `archive2.tar.gz`) holding 3 ordinary files
7. Upload both archives into the storage via **Upload** → **Upload**, so nothing is queued yet

| Steps | Actions | Expected results |
| :---: | --- |---|
| 1 | Select `archive1.zip` alone, click the selection button (**"1 item selected"**) and click **Extract archive** | A message confirms the extraction has been queued |
| 2 | Open the **Storage tasks** window (the grid-icon button at the top right of the storage view, then **Show storage tasks**) and wait until that task's status stops changing | The task's status becomes `FAILED` |
| 3 | Hover the **Status** cell of that row | A tooltip reading `The archive declares 3 entries, and 2 is the most one archive may be extracted into. Split it, or ask an administrator to raise the limit. Nothing was written to the destination.` appears |
| 4 | Look at the storage listing | No folder was created beside `archive1.zip` - the ZIP was refused before anything was extracted |
| 5 | Close the window. Select `archive2.tar.gz` alone, click the selection button and click **Extract archive** | A message confirms the extraction has been queued |
| 6 | Open the **Storage tasks** window again and wait until that task's status stops changing | The task's status becomes `FAILED` |
| 7 | Hover the **Status** cell of that row | A tooltip reading `The archive holds more than 2 entries, which is the maximum one archive may be extracted into. Split it, or ask an administrator to raise the limit. Nothing was written to the destination.` appears - worded differently from step 3, since nothing was declared up front |
| 8 | Look at the storage listing | An `archive2/` folder has appeared beside `archive2.tar.gz`, holding the 2 entries that were written before the limit was passed |
| 9 | Look at the **Actions** column of both failed rows | Neither offers a **Download** button |

**After**:
- Delete `archive1.zip`, `archive2.tar.gz` and the `archive2/` folder from the storage
- Restore the `system.async.tasks.config` preference to the value saved at step 3 of Preparations
