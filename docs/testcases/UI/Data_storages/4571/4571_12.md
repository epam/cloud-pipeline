# [MANUAL] A finished extraction raises its own notification, with no download link

Test verifies that a queued extraction task is watched like an archive download, so that when it
finishes a notification appears whatever page the user is on - naming the archive, and offering no
link, since an extraction writes into the storage itself and has nothing to hand over.

**_Note_**: **this case cannot be executed in this version.** The service that carries out an
extraction is not part of it, so a queued task never leaves its pending state and never finishes.
The GUI side is in place and this case describes it, ready for the run in which that service lands.

**Prerequisites**:
- A deployment whose service for running asynchronous archive tasks carries out extractions
- A user with **READ** and **WRITE** permissions on an S3 object storage (or an NFS storage whose
  share is mounted as NFS)

**Preparations**:
1. Login as the user from the Prerequisites
2. Open the storage from the Prerequisites
3. Upload an archive (e.g. `one.zip`) into it with **Upload**, so nothing is queued yet

| Steps | Actions | Expected results |
| :---: | --- | --- |
| 1 | Select `one.zip` and choose **Extract archive** from the selection button | A message confirms the extraction has been queued |
| 2 | Leave the storage page - open the **Library** or any other page - and wait for the task to finish | <li> A notification appears, reading `Archive "one.zip" has been extracted.` <li> It carries **no** link: nothing in it is clickable, unlike a finished archive download's `Download it` <li> It disappears on its own after a few seconds, again unlike a finished download's notification, which waits to be clicked |
| 3 | Open the storage and look at the listing | <li> A `one/` folder has appeared beside the archive, holding the archive's contents <li> `one.zip` is still there - extracting it does not delete it |
| 4 | Open the **Storage tasks** window and find that task | Its status is the successful one, its **Type** is **Extract archive**, and its **Actions** offer no **Download** |
| 5 | Queue an extraction that the service will reject - e.g. an archive whose contents would overwrite a file the user cannot write - and wait for it to finish | A notification appears reading `Extraction of "<name>" has failed.` followed by the reason the server gave |
| 6 | Open the **Storage tasks** window while an extraction is still running, and wait for it to finish with the window open | No notification appears over the window: the task's own row shows the outcome instead, exactly as for a download |

**After**:
- Delete `one.zip`, the `one/` folder, and anything left by step 5
