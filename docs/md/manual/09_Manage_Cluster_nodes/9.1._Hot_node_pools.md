> To create a node pool you need the **ROLE\_ADMIN** or **ROLE\_RUN\_ADMIN** role, or the **ROLE\_NODE\_POOL\_MANAGER** role (for a **Future dated** pool only - see [Future dated node pools](#future-dated-node-pools)). To edit or remove an existing pool you need **ROLE\_ADMIN** or **ROLE\_RUN\_ADMIN**. A **ROLE\_NODE\_POOL\_MANAGER** may also edit or remove a pool it owns.

For some jobs, the wait for a new node can be too long. It is convenient to have some running nodes in the background, which are always available, or available on a schedule.

**Cloud Pipeline** allows to keep a number of persistent compute nodes in the cluster: a certain number (**`cluster.min.size`**) of nodes of a certain size (**`cluster.instance.type`**/**`cluster.instance.hdd`**) is always available in the cluster, even if there is no workload. See the system preferences of the cluster [here](../12_Manage_Settings/12.10._Manage_system-level_settings.md#cluster).  
This speeds up the start of the runs, as the nodes are already up and running.  
"**_Hot node pools_**" make this mechanism more flexible.

## Overview

Administrators and users with the **ROLE\_RUN\_ADMIN** role can create and manage node pools in either mode. A user with the **ROLE\_NODE\_POOL\_MANAGER** role can create a **Future dated** node pool (see [Future dated node pools](#future-dated-node-pools)), and can open, edit or remove a pool it owns, but not a pool owned by somebody else.

- each pool contains _one or several identical nodes_. The pool settings define the node configuration (instance type, disk, Cloud Region, etc.) and the number of such nodes. This number can be fixed or flexible ("autoscaled")
- each pool has _a schedule of the nodes creation and termination_. E.g. most new jobs start during the workday, so there is no need to keep these nodes over the weekends. A pool can have several schedules
- each pool can have additional filters - to restrict its usage to specific users or groups, to specific pipelines or tools, etc.

When the pool is created, its nodes are started (_according to the pool's schedules_) and wait in the background. If a user starts a job at this time, and the instance requested for the job matches the pool's node, such a running node of the pool is assigned to the job.

**_Note_**: the nodes of a pool can be used by any user whose job matches the pool settings and filters.

## Node pools management

The node pools are managed at the **Hot Node Pools** tab of the **Cluster state** section.

**_Note_**: the **Hot Node Pools** tab is shown to admins and to users with the **ROLE\_RUN\_ADMIN**, **ROLE\_CLUSTER\_READER** or **ROLE\_NODE\_POOL\_MANAGER** role. A **ROLE\_NODE\_POOL\_MANAGER** uses it to create a **Future dated** pool. The neighbouring **Pools Usage** tab is shown to admins only.

The tab has a **+ Create** button and a **Refresh** button. **+ Create** is shown to admins and to users with the **ROLE\_RUN\_ADMIN** or **ROLE\_NODE\_POOL\_MANAGER** role.

### Pool creation

To create a new pool:

1. At the **Hot Node Pools** tab, click the **+ Create** button.
2. The **Create hot node pool** pop-up appears.
3. Specify the **Pool name**.
4. Specify the **Pool type**:
    - **Standard** - a pool node runs one job at a time.
    - **Shareable node** - several jobs may share one pool node, which the platform divides between them. See [Shareable pool runs configuration](#shareable-pool-runs-configuration).  
    The pool type is chosen when the pool is created. The GUI does not allow to change it later.
5. Leave the **Mode** field as **Default**. The **Future dated** mode is described in [Future dated node pools](#future-dated-node-pools) below.  
    **_Note_**: the **Mode** field is shown only to the users who may create a pool in either mode: admins and **ROLE\_RUN\_ADMIN**.
6. In the **Schedule** section, specify the pool schedule - a weekly time period during which the pool nodes are up (running and waiting for the jobs):
    - specify the day of the week and the time of the day for the _beginning_ of the period
    - specify the day of the week and the time of the day for the _end_ of the period
    - to add several periods to the pool, click the **Add schedule** button, and specify a new period as described above
    - to remove a period, click the remove button next to it  
    **_Note_**: a pool without a schedule keeps its nodes up all the time.
7. In the **Configuration** section, specify the **Nodes count** - the number of nodes in the pool, i.e. the number of nodes that run according to the schedule and wait for jobs. A pool with the count `0` is disabled.  
    You can also set the **Autoscaled** checkbox. It makes the pool size flexible: the pool size is adjusted automatically to the current cluster workload. The pool grows if most of its nodes are assigned to active runs, and shrinks if most of its nodes are idle.  
    For an **Autoscaled** pool, more fields appear:
    - **_Min Size_** - the pool size cannot go below this value. This number of nodes always runs in the cluster (_according to the schedules_). It is also the initial pool size
    - **_Max Size_** - the pool size cannot go above this value
    - **_Scale Up Threshold_** - a threshold in percent. If the percent of occupied nodes of the pool is higher than this value, the pool grows
    - **_Scale Down Threshold_** - a threshold in percent. If the percent of occupied nodes of the pool is lower than this value, the pool shrinks
    - **_Scale Step_** - the number of nodes that are added to or removed from the pool at a time  
    When you set the checkbox, **Min Size** gets the **Nodes count**. Empty threshold and step fields get the defaults: **Scale Up Threshold** - `80`, **Scale Down Threshold** - `20`, **Scale Step** - `2`.
8. Specify the **Region** (the Cloud Provider and its region) where the pool nodes run.
9. Specify the **Price type** of the pool nodes.
10. Specify the **Instance Type** of the pool nodes.
11. If you wish, specify the **AMI** of the pool nodes. It is optional. Without it, the default image of the deployment is used.  
    **_Note_**: this field is deprecated in favor of the pool's [launch configuration](#pool-launch-configuration). It still works: where the pool has a launch configuration without an `ami`, this image is used as its `ami`.
12. Specify the **Disk** size (in `Gb`) of the pool nodes.  
    **_Note_**: the pool node is assigned to a job only if the job requests a smaller disk than the pool node has. Also note that the _real_ disk size of a job is larger than the user request. E.g. if a user requests a 30 GB disk, the _real_ node disk may be 40 GB. Then a pool node with a 35 GB disk is not assigned to this job (the _real_ disk size, 40 GB, is more than the pool node disk, 35 GB). But a pool node with a 45 GB disk **is** assigned to the job. So set the pool disk with a margin.  
    On the other hand, a pool node disk can be large on purpose. Then it is not efficient to use such pool nodes for "small" requests. The **`cluster.reassign.disk.delta`** system preference sets the **max** difference between the pool node disk size and the _real_ disk size requested for a job. E.g. if the _real_ disk size of a job is 100 GB, the pool node disk is 500 GB and **`cluster.reassign.disk.delta`** is 300 GB, the pool node is not assigned to this job (the difference is more than the delta). But a job with a _real_ disk size of 250 GB **gets** the pool node.
13. If you wish, specify the Docker images that are pre-loaded to the pool nodes:
    - click the **Add docker image** button
    - select the image in the dropdown list that appears
    - select the image version in the additional dropdown list that appears
    - add more images in the same way  
    **_Note_**: the selected images are pre-loaded to the pool nodes. But such nodes can also be assigned to other jobs (with other images) if the other pool settings match the job. Then the requested image is loaded during the job initialization, which just takes longer.
14. If you wish, add labels to the pool nodes in the **Labels** field: click **Add node label**, and specify the label name and value.
15. If you wish, set filters for the pool usage in the **Filters** section.  
    The **Condition** field sets how the filters are combined: `Matches all filters ("and")` or `Matches any filter ("or")`.  
    Click the add button to add a filter, and select the property to filter by:
    - **Run owner** - restricts the pool usage to certain users
    - **Run owner group** - restricts the pool usage to certain user groups
    - **Pipeline** - restricts the pool usage to certain pipelines
    - **Parameter** - restricts the pool usage by a run parameter and its value
    - **Run configuration** - restricts the pool usage to certain detached configurations
    - **Docker image** - restricts the pool usage to certain docker images  
    For the selected property, select the condition (e.g. **Equals** or **Not equals**) and specify the value. You can add any number of filters in the same way. To remove a filter, click the remove button in its row.  
    The filters on _whose_ jobs the pool serves - **Run owner** and **Run owner group** - do not apply to the pool's own owner: a job of the user who owns the pool gets one of its free nodes as if those filters matched, even where a **Run owner** filter excludes that user. The filters on the job itself - its **Docker image**, **Pipeline**, **Run configuration** or a **Parameter** - apply to the owner as to anyone else. A pool backed by a capacity reservation adds one more condition for everyone, the owner included: a job gets its nodes only inside the reservation window.
16. Click the **CREATE** button to create the pool. While the pool is being created, the button shows a progress indicator and the form is blocked, so the request cannot be sent twice. The **SAVE** button of an existing pool works the same way.
17. The created pool appears in the list.

### Future dated node pools

A **Future dated** pool is backed by a capacity reservation of the cloud provider: its nodes are guaranteed, not subject to the usual on-demand availability. It reserves a block of capacity for a single, one-time window, instead of a weekly schedule. Currently, it is available in AWS regions only.

1. At the **Hot Node Pools** tab, click the **+ Create** button.
2. In the **Mode** field, select **Future dated**. **Default** is the pool described in [Pool creation](#pool-creation) above.  
    **_Note_**: the **Mode** field is not shown to a **ROLE\_NODE\_POOL\_MANAGER**: such a user can create **Future dated** pools only, so the pop-up opens in this mode at once.  
    **_Note_**: the **Mode** can only be chosen when a pool is created. When an existing pool is [edited](#edit-existing-pool), the field is disabled. An existing **Future dated** pool shows **Future dated** there.
3. Both pool types of [Pool creation](#pool-creation) are available. A **new** **Future dated** pool opens with one filter in its **Filters** section - **Run owner** **Equals** `<your login>` - and with the **Condition** `Matches all filters ("and")`. This is a starting point, not a fixed value: you may edit or remove it. Editing an *existing* pool never adds or changes this filter.
4. In the **Schedule** section, specify the one-time window instead of the weekly schedule:
    - **Search from** - the earliest moment the reservation may begin. Together with **Search until**, it defines a search window: the cloud provider reserves the requested **Duration (days)** somewhere inside this window, as soon as matching capacity is available. So the dates actually granted are chosen for the reservation, they are not these two values. **Search from** must be between **5** and **120** days from now.
    - **Search until** - the end of the search window: the reservation must finish by then. It must be later than **Search from**.
    - **Duration (days)** - how long the capacity is committed for, in whole days, **14** at least. It must fit between **Search from** and **Search until**. Otherwise, the form shows an error under the field.
5. Some settings are restricted for a **Future dated** pool:
    - **Spot pricing is not available** - the **Price type** is on-demand, and the field is disabled.
    - **Nodes count must be at least 1** when you create the pool. This is the number of reserved instances. Once the pool is created, **it has no nodes until the reservation is active**: the platform sets the pool node count to the reserved number when the reservation starts, and back to zero when it ends.
    - **Autoscaling is not available** - the **Autoscaled** checkbox and its fields (see [Pool creation](#pool-creation)) are not shown.
6. The other pool settings - **Region**, **Instance Type**, **AMI**, **Disk**, docker images, node labels - are specified as for a **Default** pool.
7. Click the **CREATE** button. The reservation request is created together with the pool. Depending on the [approval policies](#approval-policies), the request is approved at once, waits for an administrator's approval, or is refused. The platform may also reject the request because of provider limits (e.g. the minimum total vCPU count, or an instance family that is not allowed for reservations). Then the error is shown right after you click **CREATE**, and no pool is created.

**_Note_**: the GUI creates **Future dated** reservations only. A pool backed by an AWS Capacity Block for ML is created through the API - see [Pools backed by a capacity block](#pools-backed-by-a-capacity-block).

**Who may create what**: administrators and users with the **ROLE\_RUN\_ADMIN** role can create pools in either mode, and can edit or remove any existing pool. A user with the **ROLE\_NODE\_POOL\_MANAGER** role also sees the **+ Create** button, but can create **Future dated** pools only. Such a user may open, edit or remove the pools it owns (the ones it created), and cannot reach a pool owned by anybody else.

When you open an existing **Future dated** pool whose reservation has already been scheduled, the granted window is shown as read-only text under **Reservation window:**, instead of the **Search from** / **Search until** / **Duration (days)** controls. If the reservation is not scheduled yet, those three controls are shown disabled, with the values that were requested, and with a notice of what the reservation is doing - e.g. waiting for an administrator's approval, waiting to be placed with the cloud provider, being assessed by it - or, where it will never be placed, why: the reservation was cancelled, failed or has ended. **Nodes count** is shown as read-only text `0 out of N` (N is the reserved instance count) until the reservation is active. The **Price type** is disabled as well: neither it nor the window can be changed once the pool exists.

### View existing pools

The **Hot Node Pools** tab lists the existing node pools, their schedules, settings and states. Each pool card shows:

- the pool name
- the pool node settings (instance type, price type, disk size)
- the **Cloud Provider** / **Region** of the pool nodes
- the pool size: `N nodes`, or `Autoscaled (<min> - <max> nodes)` for an "autoscaled" pool
- in the circle: the number of pool nodes assigned to jobs at the moment, and the number of pool nodes that run at the moment (in the background or assigned to jobs)
- the list of docker images pre-loaded to the pool nodes
- the list of the pool schedules
- the buttons to edit and remove the pool, and to open its utilization. Each button appears only where it can be used: edit and remove - for an administrator, a **ROLE\_RUN\_ADMIN** or the pool owner with the **ROLE\_NODE\_POOL\_MANAGER** role; the utilization chart - for an administrator only, as the **Pools Usage** tab it opens

A pool with the node count `0` is marked `(disabled)`.

The card of a **Future dated** pool also has a reservation badge with the reservation status: _Requires approval_, _Approved_, _Assessing by cloud provider_, _Scheduled_, _Active_, _Finalizing_, _Finished_, _Purchase failed_, _Failed_ or _Cancelled_. While the reservation is not active yet, the card shows the reserved instance count as the total node count instead of `0` - e.g. `0 / 3` for a reservation of 3 instances. Such a pool is **not** marked `(disabled)`.

While a reservation is **Active**, its pool's instance type is offered as reserved capacity in the launch form - see [6. Manage Pipeline](../06_Manage_Pipeline/6._Manage_Pipeline.md#configuration) - to any user who can read the pool.

To view the pool nodes, click the pool card (this is available to the users who may edit the pool). The **Cluster state** list of nodes opens, filtered by this pool.  
The nodes of a pool are marked by a label with the pool name.  
The pool nodes that run in the background and are not assigned to jobs yet have a _Run ID_ of the form `p-<number>`.

### Edit existing pool

To edit an existing pool, click the edit button on its card. The **Edit hot node pool** pop-up opens.

You can edit only the pool name, the pool schedules, the pool nodes count (and the "autoscaled" property and settings) and the filters. For a **Future dated** pool, the name and the filters only.

Make changes and click the **SAVE** button to confirm.

### Delete existing pool

To delete a pool, click the delete button on its card. The **Delete pool** pop-up asks "**Are you sure you want to delete "`<pool name>`" pool?**".

For a **Future dated** pool whose capacity reservation is still open - any status but _Requires approval_, _Finished_, _Purchase failed_, _Failed_ or _Cancelled_ - the pop-up also shows a warning: deleting the pool cancels the reservation too, and the cloud provider may still charge for the capacity it has already committed. The **DELETE** button stays disabled until the **Force deletion** checkbox is ticked. This applies to an administrator and to the **ROLE\_NODE\_POOL\_MANAGER** who owns the pool alike.  
A **Default** pool, and a **Future dated** pool whose reservation has one of the statuses above, show no warning and no checkbox: the **DELETE** button is enabled at once.

## Pools backed by a capacity reservation

Capacity reservations are available in AWS regions only. A request to create a pool backed by a capacity reservation in a region of another cloud provider is rejected.

The API creates such a pool by a `POST /cluster/pool` request with a `capacityReservationRequest` object. An administrator or a **ROLE\_RUN\_ADMIN** can create any pool. A user with the **ROLE\_NODE\_POOL\_MANAGER** role can create a pool only when the request carries a capacity reservation: a request for an ordinary pool from such a user is refused as unauthorized.

For a future-dated reservation, the platform chooses the availability zone itself: one of the region's zones that offer the pool's instance type and that are configured in the region's `networks` (if any). If the cloud provider cannot provide the capacity for the requested date in one zone, the other zones are tried for the same date first, and then the next date. Each refusal moves the reservation on this way - whether the provider refuses the request at once, or fails, cancels or delays a reservation it has already taken. The request fails only when no start date in the requested window can fit the reservation's duration, or no zone can take the reservation at all. A payment that the cloud provider rejects fails the request at once. Moving on to the next candidate puts the request back to approval, but a reservation that needed an administrator's approval is approved only once. The owner is notified of the attempt that settles the request, not of each candidate.

Once the cloud provider has scheduled the reservation, the platform sets the pool's start date to the reservation start, and the pool's end date to the reservation end minus `finalizingLeadHours` of the **`cluster.capacity.reservation.monitor.settings`** system preference. From then on, the pool nodes take no new runs, so that no job starts on capacity that ends shortly after. Runs already on them keep running until the reservation itself ends. The platform also writes the reservation data into the pool's [launch configuration](#pool-launch-configuration):

- the reservation target, in `additional_spec` (`CapacityReservationSpecification`), so that the pool nodes consume the reserved capacity
- the reservation's `availability_zone`, and the `subnet` configured for that zone

The pool node count stays `0` until the reservation is active, so no nodes are launched before the reserved capacity exists. These fields, and the pool start and end dates, are removed when the reservation ends, fails, is cancelled, or is moved to another date or zone after a refusal: the pool is left with no nodes until a reservation schedules it again.

A pool backed by a capacity reservation cannot be autoscaled: it runs at the reserved size. Nor can it follow a schedule - the reservation window decides when its nodes are available. A request that makes such a pool autoscaled, or gives it a schedule, is rejected, at creation and in an update alike. The autoscaler does not resize such a pool.

An update request that changes any of the following is also rejected:

- the node count - it is `0` until the reservation is active, the reserved count while it is, and `0` again once it ends or is cancelled
- the price type
- the launch configuration (`amiConfiguration`), or the instance image

Other settings - e.g. the name and the filters - can be changed as for any other pool. A request that sends the current values of these fields unchanged, or does not specify the launch configuration or the instance image, is accepted. To change these settings, create a new pool with a new reservation. The pool type (`poolType`) is not in this list: an update request can switch a reservation pool between `STANDARD` and `SHAREABLE_NODE`, without giving the reservation up.

Deleting the pool gives up its reservation. A reservation that still waits for an administrator's approval has bought nothing, so it is cancelled and deleted with the pool. A reservation that the platform has already acted on - approved, or anything after that - is given up only when the request asks for it: `DELETE /cluster/pool/{id}?force=true` cancels the reservation at the cloud provider, which may cost a cancellation charge, and then deletes the pool. Without `force`, the request is rejected and names the reservation status. A reservation that has already ended, failed or been cancelled is simply deleted with the pool.

A future-dated capacity reservation shall be at least 32 vCPUs in total, e.g. 8 instances of `m5.xlarge`. A smaller request is rejected when the pool is created.

The reservation's `commitmentDuration` is requested **in seconds**, and shall be at least 14 days (`1209600`). The requested window shall be wide enough to hold it: the reservation is scheduled at a start date inside the window, and lasts for the commitment from there.

Other calls of the API (`/cluster/capacity-reservation`):

- `GET /cluster/capacity-reservation` lists the reservations, and `GET /cluster/capacity-reservation/{id}` returns one of them
- `POST /cluster/capacity-reservation/{id}/approve` approves a reservation that waits for approval. It is available to administrators only. The GUI has no approval control
- `POST /cluster/capacity-reservation/{id}/cancel` cancels a reservation. It is available to its owner and to administrators

### Approval policies

What becomes of a requested reservation is decided by the policies of the **`cluster.capacity.reservation.policies`** system preference. Each policy has an `action` and a `statement`:

- a request that matches a **`DENY`** policy is refused, and neither the pool nor the reservation is created. The error names the requested instances and says to ask an administrator
- a request that matches an **`AUTO_APPROVE`** policy, and no `DENY` policy, is approved at once
- a request that matches neither waits for an administrator's approval

A `DENY` match wins over an `AUTO_APPROVE` one, whatever order they are listed in. A request of an administrator is approved without the policies.

The statement fields are `instance.type`, `instance.count`, `commitment.duration` (in seconds), `reservation.type` (`FUTURE_DATED` or `CAPACITY_BLOCK`), `cloud.provider`, `region.id`, `owner` and `owner.authorities`. E.g. this policy refuses an AWS reservation committed for longer than 14 days:

```json
{
  "action": "DENY",
  "statement": {
    "type": "AND",
    "expressions": [
      {"type": "LOGICAL", "field": "cloud.provider", "operand": "=", "value": "AWS"},
      {"type": "LOGICAL", "field": "commitment.duration", "operand": ">", "value": "1209600"}
    ]
  }
}
```

An expression that names a field the platform does not know is skipped, with a warning in the log, and does not match. So it makes an `AND` statement - and a statement that is that expression alone - not match at all, while in an `OR` statement the other expressions still decide.

The instance types that may be reserved are set by the **`cluster.capacity.reservation.instance.families`** system preference: a JSON object keyed by the reservation type (`FUTURE_DATED` or `CAPACITY_BLOCK`). Each value is a comma-separated list of instance type patterns, in the same format as **`cluster.allowed.instance.types`** (e.g. `c5.*`). A reservation type with no entry has no restriction. The default is `{"FUTURE_DATED": "c*,m*,r*,i*,t*,g*"}`: a future-dated reservation is restricted to these families, and a capacity block is not restricted until an administrator adds a `CAPACITY_BLOCK` entry, e.g. `"CAPACITY_BLOCK": "p5.4xlarge"`.

### Pools backed by a capacity block

AWS Capacity Blocks for ML are a second kind of reservation, for accelerated capacity with the highest guarantee: a block of ML instances bought whole, for a fixed window that AWS has for sale. Unlike a future-dated reservation, there is no date to search, and a bought block cannot be cancelled. The GUI does not create such pools: use the API.

1. `GET /cluster/capacity-reservation/instance-types?regionId={id}` lists the instance types that a region sells as capacity blocks, with their vCPU count, memory and GPU, if any.
2. `POST /cluster/capacity-reservation/offerings` searches the offerings for an instance type, an instance count and a duration, with the date to start searching from and an optional end of the window. It returns what AWS has at the moment: the offering id, instance type, availability zone, instance count, the exact start and end date, the duration and the up-front price.  
    The duration is requested in hours. AWS sells blocks in specific lengths only: 1-day steps from 1 to 14 days, then 7-day steps from 14 to 182 days. The instance count must be a whole number from 1 to 64, and the start date at most 8 weeks ahead. A request outside these limits is rejected before AWS is asked.
3. Create the pool with `capacityReservationRequest.reservationType` set to `CAPACITY_BLOCK`, and with the offering's `capacityBlockOfferingId`, `availabilityZone`, start and end date (as `requestedStartDate`/`requestedEndDate`) and duration (as `commitmentDuration`, in seconds - the offering reports it in hours).

The search endpoints are available to an administrator, a **ROLE\_RUN\_ADMIN** or a **ROLE\_NODE\_POOL\_MANAGER**.

A refusal is not retried with another candidate, as it is for a future-dated reservation: if the cloud provider refuses the purchase - the offering is no longer for sale, or the payment is rejected - the request fails. To try again, search for a new offering, and submit a new request with `originId` set to the failed one. A request for no more than the failed request's commitment inherits its approval.

The minimum vCPU count applies to future-dated reservations only. The [approval policies](#approval-policies) apply to capacity blocks too, e.g. a policy on `reservation.type = CAPACITY_BLOCK`.

Deleting the pool follows the same rule as for a future-dated reservation, with one exception: once the block has been purchased, `force=true` does not help. A capacity block cannot be cancelled at the cloud provider, so the delete request is rejected until the block ends, fails, or is cancelled before the purchase. Before the purchase - waiting for approval, or approved but not yet submitted - the pool can be deleted as for a future-dated reservation. In the GUI, the **Force deletion** checkbox is shown for such a pool too, but the deletion then fails with an error.

### Extending a capacity block

A capacity block that is purchased and still active can get more time before its end - an AWS capacity block extension, not a new reservation:

- `GET /cluster/capacity-reservation/{id}/extension-offerings?durationHours={n}` searches what AWS offers to extend the block by this duration. With `findNearestAvailable=true`, the search falls back to the longest shorter duration that AWS still offers, when it has nothing for the exact duration. The offerings carry their own `capacityDurationHours`
- `POST /cluster/capacity-reservation/{id}/extension`, with the chosen offering's id as `extensionOfferingId` and the same `durationHours`, requests the extension

Both are available to the reservation owner and to administrators.

An extension can be requested from 1 hour to 57 days before the current end of the block, and only while the block is active or finalizing. Its duration follows the same AWS stepping as a purchase. There is no limit on how many extensions a block can get.

An extension is a payment that is not refunded, so it goes through the same [approval policies](#approval-policies), evaluated against its own duration: one that matches neither a `DENY` nor an `AUTO_APPROVE` policy waits for an administrator. An administrator approves it with `POST /cluster/capacity-reservation/extension/{extensionId}/approve`. Once purchased, the reservation end date moves to what AWS granted, and so does the pool end date. A failed request leaves the reservation as it was. A retry of a failed request may name it as `originId`: asking for no more than the failed request's duration inherits its approval.

### Capacity reservation notifications

The platform sends these email notifications about a capacity reservation to its owner (see [Email notifications](../12_Manage_Settings/12._Manage_Settings.md#email-notifications)):

| Notification type | Description |
|---|---|
| **CAPACITY\_RESERVATION\_REQUIRES\_APPROVAL** | a new reservation waits for an administrator's approval |
| **CAPACITY\_RESERVATION\_STATUS\_CHANGED** | the reservation status has changed |
| **CAPACITY\_RESERVATION\_FINALIZING** | the reservation ends soon. It is also sent to the owners of the runs on the pool. Its `extensionAvailable` template parameter says whether the block can still be [extended](#extending-a-capacity-block) |

The templates are shared by both kinds of reservation. A template can tell them apart by its `reservationType` parameter. The offering bought for a capacity block is the `capacityBlockOfferingId` parameter.

## Pool launch configuration

A pool may have its own launch configuration - how its nodes are started - in the `amiConfiguration` field of the pool. It has the same form as an entry of the `amis` list of the region in the **`cluster.networks.config`** system preference:

```json
"amiConfiguration": {
    "ami": "ami-0123456789abcdef0",
    "init_script": "/opt/api/scripts/init_multicloud_v1.15.4.sh",
    "fs_type": "btrfs",
    "embedded_scripts": { "fsautoscale": "/opt/api/scripts/fsautoscale.sh" },
    "additional_spec": { "IamInstanceProfile": { "Arn": "arn:aws:iam::123456789012:instance-profile/node" } },
    "availability_zone": "us-east-1c",
    "subnet": "subnet-0123456789abcdef0"
}
```

The GUI does not show this field. It is set in the pool create or update request (`POST /cluster/pool`; an update is a request with the pool's `id`):

- if a create request specifies it, it is used as is
- if a create request does not specify it, the pool has none, and its nodes are launched as the region's `amis` entries say
- if an update request specifies it, it replaces the current one. If not, the current one is kept
- the **AMI** of the pool, if specified, is used as the `ami` when the launch configuration does not specify one, and also when the **AMI** is changed later

A launch configuration needs only the fields that differ from the region's `amis` entry that the pool nodes match. The other fields are taken from that entry when a node is launched, so changes of **`cluster.networks.config`** reach the new nodes of the pool.

A specified launch configuration is checked: for an AWS region that configures `networks` in **`cluster.networks.config`**, the `availability_zone` shall be one of its zones, and the `subnet` shall be the subnet configured for that zone. A launch configuration that an update request sends unchanged - e.g. when the pool is resized - is not checked again.

When a node of a pool with a launch configuration is launched, the pool configuration is laid over the region's `amis` entry that matches the node: every field that the pool configuration sets wins, and `additional_spec` and `embedded_scripts` are merged key by key. When the node has an image of its own - the pool's **AMI** or the `ami` of its launch configuration - the `amis` entry gives only its `init_script`, `embedded_scripts` and `fs_type`: its `additional_spec` is not used, and the node gets the pool's `additional_spec` only. Set every `additional_spec` key such a pool needs (e.g. `IamInstanceProfile`) in its own launch configuration. `subnet` is a pool-only field: the pool nodes are launched into that subnet. If `availability_zone` is set and no subnet fixes it, the pool nodes are launched in that zone.

Currently, the launch configuration is applied to AWS pools only.

## Shareable pool runs configuration

A pool of the **Shareable node** type (`SHAREABLE_NODE`) lets several runs share one of its nodes. How they divide it is set by the `launchConfig` field of the pool. The GUI does not show this field:

- if a create request specifies it, it is used
- if a create request does not specify it, it is derived from the pool's instance type: CPU and RAM requests are enabled, GPU requests only when the instance type has GPUs; 1 CPU and `1GiB` of RAM are held back on each node; the run containers are privileged
- if an update request specifies it, it replaces the current one. If not, the current one is kept

An update request may also change the pool's `poolType`: switching it to `SHAREABLE_NODE` builds a default `launchConfig` as a create request without one does, and switching it to another type drops the `launchConfig`.

The runs are assigned to the pool nodes by the `pool_id` label, which every node of a pool has, with the pool's ID as its value - unless the `launchConfig` specifies a selector of its own. A run that names the pool in the `CP_CAP_POOL_ID` parameter (see [Guaranteeing a run's capacity](#guaranteeing-a-runs-capacity)) reaches a shareable pool's nodes the same way.

The `launchConfig` of other pool types is not used, and is ignored in a request.

## Guaranteeing a run's capacity

The [example below](#example-of-using) is a soft match: a run that matches a pool is assigned to one of its nodes only later, by the autoscaler, and only when a node is free. The run can still land on another node if the pool nodes are busy at the moment.

A run with the `CP_CAP_POOL_ID` parameter set to a pool's ID is bound to that pool only: the autoscaler only ever assigns it a free node of that pool - never another node, or a node of another pool. If the pool has no free node yet - because it is not active yet, or because all its nodes are busy - the run waits. The **`cluster.occupied.node.pool.wait.sec`** system preference sets how long it waits (**86400** seconds, i.e. 24 hours, by default). Then the run fails with a message that names the pool and the time it waited. With **`0`**, the run waits without a limit.

Where a free node of the pool exists and still cannot take the run, the run fails at once, on the same autoscaler cycle, rather than waiting. The failure reason names the pool and one of these reasons: the requested instance type or disk does not match the pool node; the pool's filter rejects the run; the reservation window of the pool has already ended; or the pool's end date has passed and the pool is no longer active.

Some things are checked at once, at launch: `CP_CAP_POOL_ID` must be a valid pool ID, the pool must exist, and if the run asks for an instance type or a region explicitly, it must be the pool's own. Otherwise the launch is rejected, with the reason.

A pipeline's `config.json` may set a default value of `CP_CAP_POOL_ID`, as of any other parameter. If the named pool is a [shareable pool](#shareable-pool-runs-configuration), the run gets that pool's node selector automatically.

`CP_CAP_POOL_ID` is optional: a run without it keeps the soft matching described below.

## Example of using

1. For example, there is a node pool that was created as described [above](#pool-creation).
2. A user launches a tool (at a time inside the pool schedule) with settings that match the pool node settings: the same region, instance type and price type, a smaller _real_ disk size, and **in accordance with all the pool filters**.
3. After the launch, the system checks whether there are free nodes in the cluster. If not, the system checks whether there are free nodes in the "**hot node pools**" that match the job, and uses such a pool node if it matches.  
    So, the running node of the hot node pool is assigned to the job after just several seconds.  
    Please note that the disk of the run is changed to the disk of the pool node.
4. Click the **IP** link of the run to open the node info. The node has the label with the pool name.
5. Open the **Hot Node Pools** tab of the **Cluster state** section. The pool state has changed: one of its nodes is occupied.

## Example of using of the "autoscaled" node pool

1. Open a pool with a static size for editing.
2. Set the **Autoscaled** checkbox.
3. Specify the autoscaling settings, e.g. **Min Size** `3`, **Max Size** `7`, **Scale Up Threshold** `60`, **Scale Down Threshold** `30`, **Scale Step** `2`.
4. Save the changes.
5. Launch at least 2 runs with settings that match the pool node settings, to occupy 2 of the 3 nodes.
6. As the percent of occupied nodes of the pool (67%) is higher than the **_Scale Up Threshold_** (60%), the pool grows by the **_Scale Step_** (2) after some time.

## Pool utilization

Admins can also:

- view charts of the hot node pools utilization per day or per month
- enable the email notification about the event when all nodes of a pool are used (`FULL_NODE_POOL`)

The hot node pool utilization is shown at the **Pools Usage** tab of the **Cluster state** section.

This tab has:

- a chart of the utilization of all hot node pools (_left_ chart):
    - a line for each hot node pool - with the time on the X-axis and the pool utilization (in **percent**) on the Y-axis
    - hover a point of a pool line to see the time range of the point, the pool name and the maximum utilization (in _percent_) of that pool in that time range - i.e. the ratio of the maximum number of busy nodes to the total possible number of nodes in that time range
- a chart of the utilization of the selected hot node pool (_right_ chart):
    - two lines - with the time on the X-axis and the number of nodes under load on the Y-axis:
        - the first line is the utilization of the selected pool. Select the pool in the dropdown list above the chart. By default, the first pool (in alphabetical order) is selected
        - the second line is the limit of the selected pool, i.e. the maximum possible size of the pool in that time range
    - hover a point of the utilization line to see the time range of the point, the pool name and the maximum number of nodes under load
    - hover a point of the limit line to see the time range of the point and the maximum possible size of the pool

By default, the charts are shown for today. Use the calendar control above the charts to select another day. The period can be changed from _Day_ to _Month_ with the control above the charts. Then the charts are shown for the current month, and the calendar control selects another month.

### Navigation from the Hot node pool tab

You can open the utilization of a certain pool from the **Hot Node Pools** tab: click the chart button on the pool card.

Then:

- the **Pools Usage** tab opens
- the left chart shows the utilization of all hot node pools
- the right chart shows the utilization of the selected pool (the pool whose card you clicked)
