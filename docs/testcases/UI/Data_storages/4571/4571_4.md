# "Upload and extract" uploads the batch, then queues extraction and closes

Test verifies that choosing **Upload and extract** on the **Upload files** pop-up uploads every
picked file exactly like **Upload** would, then queues one extraction task per uploaded archive and
tells the user where to follow them, closing the pop-up the same way an ordinary upload closes - it
does not stay open waiting for the extraction to run. It also verifies that the message's **Show
storage tasks** wording is a clickable link that opens the **Storage tasks** window, and that each
queued task is listed there as an **Extract archive** task, naming where its contents would go.

**_Note_**: the service that carries out an extraction is not part of this version. A queued task is
listed in the **Storage tasks** window and stays in its pending state, so this case checks that the
tasks are queued and listed - not that any extracted file appears in the storage.

**_Note_**: once that service exists, each archive is extracted into a **new folder beside it named
after the archive without its extension** - `archive1.zip` into `archive1/`, `archive2.tar.gz` into
`archive2/` - and the archive itself is **kept**, not deleted.

**Prerequisites**:
- A user with **READ** and **WRITE** permissions on an S3 object storage (or an NFS storage whose
  share is mounted as NFS)

**Preparations**:
1. Login as the user from the Prerequisites
2. Open the storage from the Prerequisites
3. On the local machine, have ready two archive files (e.g. `archive1.zip`, `archive2.tar.gz`) and
   one ordinary file (e.g. `file1.txt`)

| Steps | Actions | Expected results |
| :---: | --- | --- |
| 1 | Click the **Upload** button, select all three files from Preparations together in the OS file dialog and confirm | The **Upload files** pop-up opens, listing all three files by name only, and the **Cancel**/**Upload and extract**/**Upload** buttons |
| 2 | Look at the buttons the moment the pop-up opens | **Upload** and **Upload and extract** are briefly unavailable while the archive-task allowance is checked, then both become available. **Cancel** is available throughout |
| 3 | Click **Upload and extract** | The pop-up switches to the progress view, titled **Uploading files...**, with a progress row per file - same as an ordinary upload |
| 4 | Wait for all three files to finish uploading | <li> A loading message reading `Starting archive extraction...` appears briefly <li> It is replaced by a message reading `Extraction of 2 archives has been queued. Follow their progress under "Show storage tasks".`, with **Show storage tasks** rendered as a clickable link <li> At no point does the pop-up's title change to anything about extracting, and no status line about extraction appears inside the pop-up itself |
| 5 | Before the message disappears on its own, click the **Show storage tasks** link inside it | The message closes, and the **Storage tasks** window opens |
| 6 | Look at the table in the **Storage tasks** window | <li> Two new rows are listed, one per uploaded archive <li> Each has **Extract archive** in the **Type** column <li> Each names its own archive - `archive1.zip` and `archive2.tar.gz` - with no item count in brackets after the name <li> Each shows the storage from the Prerequisites, a pending status, and no size |
| 7 | Look at those two rows' own **Actions** | Each offers a **Cancel** button and no **Download** button |
| 8 | Close the **Storage tasks** window and look at the pop-up | The pop-up has closed on its own, the same way an ordinary upload's pop-up closes |
| 9 | Look at the storage listing | <li> `file1.txt`, `archive1.zip` and `archive2.tar.gz` are all present, each as the file that was uploaded <li> No `archive1/` or `archive2/` folder has appeared: the tasks are queued but nothing runs them in this version (see the note above) |

**After**:
- Cancel both extraction tasks in the **Storage tasks** window
- Delete `file1.txt`, `archive1.zip` and `archive2.tar.gz` from the storage
