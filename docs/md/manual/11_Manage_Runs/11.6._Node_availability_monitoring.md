## Overview

A compute node may stop responding while its run is still in the `RUNNING` state — the instance is
terminated outside the Platform, the host loses its network, or the `kubelet` on it dies. When the
instance is gone, the run stops making progress, but its status does not change: its last task stays in
progress and no log is added, so without a separate monitor such a run would hang until somebody stops
it by hand.

The Platform therefore watches the availability of every node it owns, marks the runs of the nodes that
stopped reporting, and eventually stops those runs.

When only the `kubelet` has died, the job may still be running in its container, but the Platform can
no longer tell how it is doing. Such a run is stopped all the same once the
[grace period](#the-grace-period) is over, so a job that must not be lost this way needs a longer grace
period — see [Overriding the grace period for a single run](#overriding-the-grace-period-for-a-single-run).

The monitoring is a part of the autoscaler, and runs only if the **`cluster.enable.autoscaling`**
preference was enabled when the API server started. The preference is read once, at the start, so a
change to it takes effect after the API server restarts.

## How a node becomes unavailable

The Platform relies on the state the Kubernetes cluster itself reports for a node. The `kubelet` on
every node keeps reporting the node's `Ready` condition. When it stops, the cluster sets the status of
that condition to `Unknown`, and the Platform treats the node as **unavailable**. A node that has no
`Ready` condition at all is treated as unavailable as well.

It is specifically the node having stopped reporting that counts. A node that is still reporting, and
reports itself as not ready, is **not** treated as unavailable: its run is left alone, because such a
node routinely comes back on its own and terminating it would cost a user their job for a transient
condition. For the same reason, a node that keeps reporting is not treated as unavailable when it runs
low on memory or disk space.

Nodes in the following cases are not monitored:

- **paused** nodes — a paused run has no running instance by design
- nodes of the **local** cluster — those are not managed by the Platform's autoscaler

## What the run shows

Once a node is recognised as unavailable, the run using it gets the following — before the node is
stopped, and even if its grace period has already expired by the time the node is first checked:

- the **`NODE_UNAVAILABLE`** tag, shown as a label next to the run in the **Runs** page and at the top
  of the run's own page
- a companion tag holding the moment the node went out of order. Its name is the tag name plus the
  suffix from the **`system.run.tag.date.suffix`** system preference — `NODE_UNAVAILABLE_date` with the
  default suffix
- a **`NodeAvailabilityMonitor`** task in the run's log, with the
  `Node <node> has been unavailable since <date>` entry

The labels are displayed for active runs only. Once the node is stopped and its run fails, the run is no
longer displayed with them, and the `NodeAvailabilityMonitor` task in its log is what tells why it failed.
A node whose grace period has already expired when it is first checked is stopped on that same check, so
its run fails without ever being displayed with the label.

If the node starts reporting its state again before it is stopped, the tags are removed and the
`NodeAvailabilityMonitor` task records `Node <node> has been available since <date>` instead. The run
continues.

## The grace period

A node is not stopped the moment it goes quiet — a short network interruption shall not cost a user
their job. The Platform waits for a **grace period**, counted from the node's last report, and only
stops the run if the node has not come back by then.

The grace period is set by the **`cluster.node.unavailable.grace.period.minutes`** system preference,
in the **`Cluster`** group of the **Preferences** (see
[12.10. Manage system-level settings](../12_Manage_Settings/12.10._Manage_system-level_settings.md) for
details on editing preferences). Its default is **30** minutes. With `0`, an unavailable node is stopped
on the check that first finds it, right after its run is tagged and the `NodeAvailabilityMonitor` entry is
written to its log.

Once the grace period has elapsed, the node is scaled down, and the run it backs fails. A free node of a
[hot node pool](../09_Manage_Cluster_nodes/9.1._Hot_node_pools.md) has no run to fail and is simply
removed from the pool; once such a node serves a run, that run fails like any other.

The Platform may also stop waiting early. On the pass that first marks the node unavailable — and only
on that pass — it asks the Cloud Provider for the state of the node's instance, and scales the node down
immediately if the provider reports anything other than `running`: an instance that is stopped, stopping
or already terminated is not going to resume reporting, so there is nothing left to wait for.

The grace period is not exact. The node's last report is the moment the `kubelet` last refreshed the
`Ready` condition, and while nothing changes on the node, the `kubelet` refreshes it only every few
minutes — so the grace period may run out a few minutes earlier than its value says, and a grace period
of only a few minutes may stop a node on the check that first finds it, as `0` does. The check itself
runs on the autoscaler's schedule, set by the
**`cluster.autoscale.rate`** preference (`40000` milliseconds by default), so a node is stopped on the
first check after its grace period is over.

## Overriding the grace period for a single run

A specific run may need a longer tolerance than the deployment's default — for example a job whose node
sits behind an unreliable link. The **`NODE_UNAVAILABLE_GRACE_PERIOD_MINUTES`** system parameter sets the
grace period for a single run, in minutes.

To use it, open the **Advanced** tab on the **launch page**, click the **Add system parameter** button,
find `NODE_UNAVAILABLE_GRACE_PERIOD_MINUTES` in the opened popup and set its value. The parameter is
passed to the worker nodes of a cluster run as well.

The value shall be a whole number of minutes, from `0` to `2147483647`. Anything else — a negative
value, one with a sign or a space in it, or one too large — is ignored, and the
`cluster.node.unavailable.grace.period.minutes` preference applies instead.
